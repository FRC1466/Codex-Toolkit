# 1466 subsystem preferences

## How to work

Prioritize getting the mechanism ready for a hardware test. Choose and briefly explain ordinary, reversible design decisions. Ask before major changes such as replacing the robot-wide architecture, changing a shared interface across multiple mechanisms, or switching the project's autonomous library. Use judgment on nearby cleanup. Report incidental changes when they affect behavior, add risk, or deserve the maintainer's attention.

For students who know Java from AP Computer Science A, teach through a real subsystem assignment. Explain the behavior, the flow from request to output, and how you'll check it. Let the student choose the depth of the explanation. Then implement the whole requested subsystem and run the appropriate software checks. Ask about hardware facts when they affect the implementation. Show the student where to follow the control flow in the diff. Keep explanations centered on FRC and the project's code unless the student asks about Java itself.

## Build and bring up mechanisms

When asked for a short-lived prototype, build the smallest version that can answer the hardware question. AdvantageKit setup and replay are optional for that prototype. Apply the integrated logging and replay standard when the code is intended to stay or is promoted into the robot project.

Start close to 1466's 2026 subsystem and IO split. For an indexer or similar new mechanism, prefer one package with a mechanism class for decisions and an IO interface for inputs and outputs. Build both simulation IO and real IO when the intended hardware is known, even if it has not arrived. When the hardware choice is still unknown, build the mechanism, its IO interface, and simulation IO only. In 2026, `Indexer`, `IndexerIO`, `IndexerIOTalonFX`, and `IndexerIOSim` showed the layout. Use the current repo's equivalent abstractions. For early position simulation, a simple rate-limited transition from the current position toward the goal is sufficient. Label the model and use it to check behavior and sequencing.

Provide a simple manual bring-up mode for each mechanism whose constants are unknown. Let the operator request bounded motion or enter one position or velocity setpoint at a time, read the response, and tune gains. Keep automatic sequencing and motion based on unknown limits out of that mode. If a device is selected but critical wiring, position reference, or motion bounds are unknown, leave those parameters explicit and enable only the controls supported by verified facts. Keep stop and cancel behavior obvious.

Prefer keeping mechanism-specific configuration in the subsystem's folder, including CAN IDs, inversion, gearing, and travel limits. Follow the project's wiring map, bus definitions, or robot profile when those are shared across mechanisms. Keep one source of truth so the same value does not silently diverge between real IO, simulation, and behavior. Hardware settings come from the current mechanism and revision.

Prefer WPILib unit types for new physical quantities in agent-written interfaces. Preserve existing APIs and accept student-written primitives with clear units in their names and contracts, such as `angleDeg` or `velocityRps`. Do motor-to-mechanism gearing conversions at the IO boundary, using either vendor feedback scaling or explicit conversion as appropriate. Check that the ratio is applied exactly once and that real and simulation IO expose the same mechanism-side quantities.

Require a fresh press after re-enable for momentary controls such as held roller buttons. Test the case where a button stays held through disable and re-enable. Keep the pivot's intended position goal on disable and resume that goal on enable when the sensor, homing or calibration where required, and interlocks permit it. Restore the goal through normal motion limits and control. If the mechanism cannot establish a valid position, follow its homing or fault behavior first.

Prefer closed-loop control on the motor controller when it supports the mechanism's needs. Prefer CTRE Motion Magic for profiled position moves on compatible controllers. Make setpoints, gains, tolerances, delays, and other frequently adjusted values live tunables behind an explicit tuning mode, following the 2026 convention. Use 1466's `LoggedTunableNumber` where the project currently uses it. Use configured defaults outside tuning mode and keep wiring and fixed hardware facts in configuration. Evaluate the [WPILib 2027 Tunables API](https://github.com/wpilibsuite/allwpilib/blob/main/tunables/doc/tunables.md) against the actual project dependencies before switching. For integrated code, record the effective tuning inputs and verify that a mid-run edit and its effect replay at the right time before migrating from the logged path.

## Faults, diagnosis, and review

Use timeouts for actions that could otherwise wait indefinitely. A timeout or failed prerequisite should end the affected action, leave the mechanism in its defined stop or hold state, and clearly tell the operator what failed. Use the project's alerts or an equally visible indication during practice. Skip speculative fallbacks, silent retries, and alternate routines that hide a failure. Add an alternate only when the team specifically asks for that behavior.

For an unexpected behavior report, inspect the relevant code and configuration first. Fix a clear in-scope cause when asked to fix the issue. If the code looks correct or cannot distinguish the causes, ask for the smallest useful log window or observation.

Use AdvantageKit in integrated code and design every behavior to replay from recorded inputs. Log sensor values, status, and faults through IO and `Logger.processInputs()` before using them in control. Use replay-aware time and documented built-in inputs for Driver Station and controller state. Treat other external inputs, including dashboard edits and coprocessor data, as replay inputs. Log requested goals, resulting states or outputs, effective settings, and why significant transitions happen. At the first reasonable opportunity, replay a representative run on the same code and compare key outputs. Report which parts have replay support and which have actually been checked. See [AdvantageKit dashboard inputs](https://docs.advantagekit.org/data-flow/recording-inputs/dashboard-inputs/) and [sources of replay nondeterminism](https://docs.advantagekit.org/getting-started/common-issues/non-deterministic-data-sources/).

Keep the merge handoff lightweight. Confirm the robot project compiles and tell 1466's designated maintainer what changed and what needs testing. Codex can prepare and open a PR when authorized. The designated maintainer manually clicks Merge on GitHub after the compile passes. Leave formal review approvals optional. Leave the PR open for the maintainer, including when Codex is authenticated as them. Do not enable auto-merge or merge on their behalf. Use existing checks when useful. New automated tests are optional and should be rare. Add a focused one when requested or when it catches a specific consequential regression cheaper than checking it another way.

## Autonomous and coordination

BLine is the current candidate for autonomous path following. Use the planner already chosen in the robot repository and confirm its version and compatibility before adopting a new one. Describe an auto in a short plain-text sequence with its start, drive and mechanism actions, completion conditions, and when it stops or reports failure. See [BLine installation and compatibility](https://docs.bline.run/getting-started/installation/).

The team likes the 2026 `Choreographer` as an example of coordinating several mechanisms. The 2027 choice of coordination and scheduling is open. Use the current architecture if it exists. Otherwise keep mechanism behavior and IO reusable while the team evaluates a coordinator, command composition, or an explicit state machine. Check the actual project dependencies before writing framework-specific code. Whatever the arrangement, identify who owns the mechanism output and what happens when control changes hands, an action is cancelled, or the robot is disabled.
